# Milestone 7.6D.9 — Two-witness finality authorization (test-only)

**Status:** Experimental; **not a proof of Solana finality** and **not production-ready**. This is a PostgreSQL authorization prototype that assumes two independent trusted finality observers. No live broadcast is enabled, no signing key is committed, and no existing AgentVault executor is changed.

## Threat boundary

A compromised finalizer login could previously supply a made-up finalized slot directly to the guarded PostgreSQL function. D.8 quarantines that function so it only writes `SUBMISSION_RESERVED → UNRESOLVED`. The D.9 test-only installer **requires this quarantine** and adds a separate `agentvault_model_b_attested_finality_guarded` function which can write `CONFIRMED` or `FAILED` only if two distinct, independently held 256-bit witness HMAC keys authenticate exactly the same terminal observation. A finalizer cannot read these keys, insert keys, or call the original function to bypass the quarantine. Terminal updates remain irreversible.

The signed canonical message includes the domain/version, request ID, Solana genesis hash, program ID, vault address, workflow/payment digests, SHA-256 hash of immutable saved transaction bytes, original transaction signature, last valid block height, terminal outcome, and finalized slot. Each UTF-8 field is byte-length-prefixed to prevent ambiguous concatenation. PostgreSQL recomputes the authenticated message from its locked payment record rather than trusting caller-supplied identity fields. It verifies the saved bytes' SHA-256, both independent HMACs via the `pgcrypto` extension, and a one-way `SUBMISSION_RESERVED` or `UNRESOLVED` to terminal transition. Evidence replay, mismatched slot, ledger, request ID, payment bytes or status cannot create another terminal update.

## Trust assumptions and limitations

- HMACs authenticate **witness claims**, not consensus proofs. An actual witness MUST independently obtain finalized Solana status and the matching transaction receipt, verify the correct genesis, signature, slot, transaction error, and original payment identity, and fail closed on contradictions **before signing**. This milestone deliberately does **not** implement those separate observer services or a second RPC implementation.
- The two observers must have separate process credentials, signing keys, operators and independent data sources; common-mode RPC compromise or colluding/compromised witnesses can still forge agreement. A witness must not use the finalizer's RPC response as its sole source of truth. A finalizer must never possess either witness key. The test uses two random synthetic keys and fake finality; it **cannot** establish that an actual chain transaction settled.
- The PostgreSQL table owner/DBA can read both symmetric HMAC secrets and can bypass SQL restrictions. This is an explicit **DBA trust assumption**, not independence from database administrators. Before considering production, replace shared-secret custody with an independently operated asymmetric verifier / hardware or external proof gate, review key rotation/revocation, avoid SQL timing oracles, and independently audit the SQL privilege and function ownership surface.
- The legacy privilege audit intentionally rejects an unexpected SECURITY DEFINER function. After D.9 installation, that historical audit must not be treated as evidence of safety; a reviewed extended privilege audit is needed. This prototype is intentionally incompatible with production approval and must not silently weaken existing audit checks.
- The new terminal function is **not wired** to the TypeScript finalizer. Existing finalizer SQL attempts remain quarantined, and no real Model B payment can acquire terminal status through the old API in a quarantined schema. A separate reviewed witness operation and finality client are required.

## Safe verification

The new test requires `AGENTVAULT_TEST_DATABASE_URL` and `AGENTVAULT_MODEL_B_TEST_FINALIZER_URL` configured for the existing, dedicated local `agentvault_test*` database. It creates a unique private schema and runs the old guarded migrations, D.8 quarantine, then D.9. If `pgcrypto` is absent, the test attempts to install it **inside that disposable schema** and drops it with the schema afterwards; it does not modify the live application schema. No witness keys appear in the Git patch or disk artifacts: the test generates random ephemeral secrets, inserts them only as the test schema owner, and destroys the entire disposable schema afterwards.

**Do not manually run the installer or persist keys in your normal test/application schemas.** Production use requires independently operated witness services, custody and evidence standards, cross-process and live Devnet integration tests, a revised privilege audit, a reviewed migration, and an independent security assessment. Remain fail-closed and unresolved when two trustworthy witnesses cannot agree.
